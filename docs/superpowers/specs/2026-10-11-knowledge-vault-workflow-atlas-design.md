# 知识库完整工作流地图设计

日期：2026-10-11  
状态：等待用户审阅  
目标：把知识库从“文件与技能清单”升级为可按工作目的浏览、可追溯、可验证的交互式工作流地图。

## 1. 用户目标

用户需要看到的不只是仓库目录或技能名称，而是每类工作实际如何完成。系统必须同时回答：

1. 这项工作的目的是什么？
2. 什么条件下应该启动？
3. 需要哪些输入和证据？
4. 底层判断逻辑是什么？
5. 执行步骤、分支和停止条件是什么？
6. 哪些动作必须人工授权？
7. 产出是什么，如何验收？
8. 失败、信息不足或外部受限时如何处理？
9. 哪些技能、脚本、模板和知识文件支撑这条流程？

## 2. 范围

### 2.1 纳入范围

- 仓库中允许发布的全部工作目的和可迁移技能。
- 邮件与客户开发、外贸研究、市场与客户研究、电商、独立站、自媒体、内容蒸馏、视觉设计、软件开发、测试、质量审计、部署准备、自动化、知识管理和跨设备恢复。
- 每个技能必须有用途、触发条件、输入、核心逻辑、输出、依赖、风险边界和所属流程。
- 每个工作目的必须有一条可执行、可验证的完整流程。

### 2.2 排除范围

- 用户明确排除的品牌专项技能和车辆膜领域内容。
- Candy 相关研究、成人内容研究及其衍生提示词或工作流。
- 密码、令牌、Cookie、API Key、邮箱内容、浏览器资料和原始客户敏感记录。
- 未经确认的价格、参数、认证、联系方式、发送结果、部署结果和平台状态。
- 大型原始素材、缓存、临时验收文件和运行时锁文件。

### 2.3 真实性边界

- `inbox/` 内容保持 `UNVERIFIED`，不能直接升级为已验证流程事实。
- 工作流状态必须保留 `PASS`、`WATCH`、`FAIL`、`BLOCKED` 和 `UNVERIFIED` 区别。
- 草稿、预演和本地验证不能表述为已发送、已发布、已部署或已成交。
- 真实邮件、社交操作、线上商店修改、部署、发布、购买和账号变更必须有明确的当次授权。

## 3. 信息架构

成品采用三层结构。

### 3.1 第一层：工作目的总览

总览按用户想完成的事情组织，而不是按文件夹或工具品牌组织。初始领域如下：

1. 客户与市场研究
2. 邮件与合规触达
3. 外贸销售与客户跟进
4. 选品、核价与商品准备
5. 独立站与电商运营
6. 自媒体与内容生产
7. 内容采集、转写与知识蒸馏
8. 视觉设计与前端体验
9. 软件规划、开发与调试
10. 测试、审查与质量门
11. 部署准备、监控与恢复
12. 自动化与代理协作
13. 知识库维护与跨设备迁移

领域允许在证据盘点后拆分，但不得仅为缩短页面而合并语义不同的工作。

### 3.2 第二层：工作流详情

每条工作流使用统一结构：

`目的 -> 触发 -> 输入 -> 证据检查 -> 判断逻辑 -> 执行步骤 -> 人工授权门 -> 输出 -> 验收 -> 失败处理 -> 状态沉淀`

邮件类流程至少拆分为：目标客户筛选、公开背景核验、联系方式质量门、个性化草稿、合规与抑制检查、人工确认、受控发送、提供商证明、回复分类、后续跟进和知识回写。没有当次发送授权时，流程必须停在草稿或预演状态。

### 3.3 第三层：技能明细

每个纳入技能生成一张技能卡，字段为：

- `id`：稳定标识。
- `name`：技能名称。
- `purpose`：解决什么问题。
- `when_to_use`：触发条件。
- `inputs`：必需输入和可选输入。
- `logic`：关键判断、顺序、门禁和停止条件。
- `outputs`：文件、报告、代码、截图或状态更新。
- `dependencies`：脚本、运行时、外部服务和其他技能。
- `authorization`：是否涉及发送、发布、部署、账号或付费动作。
- `validation`：如何证明完成。
- `failure_modes`：常见失败和降级方式。
- `workflow_ids`：所属工作流。
- `source_paths`：仓库证据位置。
- `completeness`：`PASS`、`WATCH`、`FAIL` 或 `UNVERIFIED`。

同名技能可有多个来源，但必须分别记录来源路径；只有内容哈希一致时才可标记为副本。

## 4. 交互式成品

稳定发布目录为 `docs/workflows/`：

```text
docs/workflows/
  index.html
  README.md
  workflow-catalog.json
  skill-catalog.json
  coverage-report.json
  diagrams/
    workflow-overview.html
    <workflow-id>.html
  sources/
    <workflow-id>.json
```

### 4.1 总入口

`index.html` 是离线可打开的入口，提供：

- 按工作目的浏览。
- 按技能名称、用途、输入和输出搜索。
- 按 `PASS/WATCH/FAIL/BLOCKED/UNVERIFIED` 筛选。
- 从工作目的进入工作流，再查看关联技能。
- 从技能反查它参与的全部工作流。
- 显示覆盖率、缺失说明、缺少依赖和未验证项目。

页面不得依赖 CDN、在线字体、远程脚本或 GitHub Pages；克隆仓库后直接打开即可使用。

### 4.2 Archify 图

- 一个 Archify 架构图展示“工作目的、知识证据、技能、执行门禁和结果沉淀”的整体关系。
- 每个工作目的至少对应一张 Archify 工作流图。
- 图中的事实必须引用仓库内来源，并固定到生成时的 Git 提交。
- Archify 的 `finalize`、严格来源检查和真实浏览器检查必须通过。
- 桌面明暗主题必须做实际截图检查；移动端检查入口、搜索和文本可读性。

### 4.3 GitHub 使用方式

- Private Git 仓库只负责版本保存和跨设备同步。
- README 明确说明 GitHub 文件页不会直接运行交互 HTML。
- 用户克隆后本地打开 `docs/workflows/index.html` 使用完整交互功能。
- 不启用 GitHub Pages，除非用户以后单独授权。

## 5. 数据生成与更新流程

1. 读取 `PROFILE.md`、`KNOWLEDGE_INDEX.md`、`TASK_STATE.md` 和项目页。
2. 读取技能清单和每个纳入技能的完整 `SKILL.md`，不能只根据目录名生成描述。
3. 提取技能元数据、步骤、依赖、限制和验证方法。
4. 应用排除规则和敏感信息扫描。
5. 将技能映射到一个或多个工作目的。
6. 从知识页、项目交接和技能正文构建工作流，不把未验证材料当事实。
7. 生成 JSON 目录、覆盖报告、离线入口和 Archify 图。
8. 运行结构、链接、来源、秘密、覆盖率和浏览器验证。
9. 只有全部门禁通过后才更新导航和任务状态并推送 Git。

生成器必须可重复运行；相同输入应保持稳定 ID，避免每次更新产生无意义的大规模差异。

## 6. 覆盖和质量门

### 6.1 技能覆盖

- 每个允许发布的技能必须恰好有一张主技能卡。
- 每张技能卡至少归入一个工作流。
- 没有足够正文证据的技能标记为 `UNVERIFIED`，不能自动补造逻辑。
- 缺脚本、模板、依赖或引用文件时标记 `WATCH` 或 `FAIL`，并记录缺口。

### 6.2 工作流覆盖

- 每个工作目的必须至少有一条端到端流程。
- 每条流程必须包含输入、判断、动作、输出、验收和异常路径。
- 涉及外部副作用的流程必须有清晰的人工授权节点。
- 分支、重试、停止和降级必须在图或流程详情中可见。

### 6.3 自动验证

- `python -m unittest discover -s tests -p 'test_*.py'`
- `python scripts/validate_vault.py .`
- 新增工作流目录的 JSON Schema 和交叉引用测试。
- 排除词、秘密模式、断链、重复 ID、孤立技能和孤立工作流检查。
- `git diff --check`
- Archify `finalize` 与严格来源检查。

### 6.4 人工验收

- 抽查邮件、研究、建站、内容、开发、测试、部署和知识迁移流程。
- 确认用户能从“我想完成什么”找到流程，而不需要先知道技能名。
- 确认技能卡能解释底层逻辑，而不只是复述技能简介。
- 确认总览不拥挤，详情文字不截断，桌面和移动端均可读。

## 7. 错误处理

- 来源缺失：保留技能卡，状态设为 `UNVERIFIED`，列出需要补读的文件。
- 依赖缺失：不安装大型依赖；记录预计大小、默认位置和 D: 替代方案，等待用户确认。
- 流程冲突：保留各来源结论，显示冲突，不自行选择一个为真。
- 技能重复：以来源路径和哈希区分；不因名称相同直接删除。
- 图过密：拆成领域子图，保持总览只展示目的和跨领域关系。
- 验证失败：不推送，不把状态写成 `PASS`。

## 8. 实施边界与交付顺序

1. 建立稳定数据模型和验证器。
2. 生成完整技能目录和覆盖报告。
3. 建立工作目的分类与端到端流程。
4. 生成离线交互入口和 Archify 图。
5. 完成自动与视觉验收。
6. 更新 `README.md`、`KNOWLEDGE_INDEX.md` 和 `TASK_STATE.md`。
7. 在隔离分支提交，只把本任务文件推送到 Private Git。

本设计不删除或改写仓库已有知识；它新增一层可执行导航，并以来源链接回到原始知识、技能和项目状态。
